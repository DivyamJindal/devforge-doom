EgoMem: a DOOM agent that remembers where it has been

Yugaantar 2026 · DevForge Track 1 "Can It Play DOOM?" · github.com/DivyamJindal/devforge-doom

USP: a recurrent agent with an episodic place memory (rotation-invariant scene signatures, so "I have been here" needs no coordinates), trained with our own asynchronous recurrent PPO on an endless stream of procedurally generated levels that mirror the four hidden tiers. It never sees the same layout twice, so it has to learn to play DOOM rather than memorise maps. Every action comes from the network: no pathfinding, no rule trees, no aimbot.

01Neural architecture

ComponentWhat it doesWhy (vs the usual approach)
Circular ray CNN3 Conv1d layers with circular padding over the 64-ray ring (distance + one-hot hit type: wall, door, locked door, enemy, item).The ring has no start or end. A plain CNN or MLP treats ray 0 and ray 63 as far apart; ours sees an obstacle behind-left the same wherever it falls.
Entity set encoderPer-entity MLP over (distance, sin/cos angle, relative velocity, type), then masked attention pooling + max pooling.Permutation-invariant and handles 0–32 enemies, items or projectiles: answers "variable numbers of enemies" directly. Padding cannot leak in (unit-tested).
Episodic place memoryEvery 2 steps it stores a 19-D signature of the surroundings: FFT magnitude of the ray ring + hit-type histogram. Each step outputs novelty (distance to the nearest stored place), familiarity (number of near matches) and steps since last novel place.Rotation-invariant by construction (FFT magnitude ignores ring shifts), so turning on the spot does not look like a new place. Needs no coordinates. We first tried velocity dead-reckoning for a metric map; it drifted ~800 map units in 300 steps, so we dropped it for place recognition.

GRU core + macro-actionsGRU(256) integrates everything over time. 15 macro-actions over the 9 buttons; USE is pulsed because it fires only on 0 → 1 and re-pressing reverses a moving door.Respects the engine quirks the organisers flagged. 02Spatial memory design in one paragraph

DOOM is partially observable: the agent sees a 90° cone and a ring of rays, never a map. EgoMem keeps three memories at different time-scales. The GRU holds the last few seconds (where the enemy went, which way I was turning). The event memory holds facts that must survive hundreds of steps (a locked door exists; which keys I hold). The episodic place memory holds the whole episode's set of places, so the policy can tell a new corridor from one it already searched. Its novelty signal also drives an intrinsic curiosity bonus during training (NGU-style), which uses only the agent's own observations and therefore transfers to any map.

Training and exploration pipeline

Our own recurrent PPO · procedural curriculum · asynchronous workers on Modal · held-out evaluation

03Procedural levels: no map is seen twice

Only one test map ships with the template, so we wrote a level generator (training/mapgen.py). It produces random room + corridor dungeons in the organisers' own UDMF conventions: doors (special 12), locked doors (special 13 + ZDoom lock), exit lines (special 243), keycards, monsters, health, ammo, weapons and armour. There are five tiers:

  • 0 on-ramp: small, few monsters (curriculum start)
  • 1 combat: dense monsters in connected arenas
  • 2 exploration: 6–12 rooms, doors, dead ends, far exit
  • 3 progression: 1–2 key → locked door chains guarding the exit, keys in side branches
  • 4 gauntlet: tier 3 + more monsters, scarcer items

A flood-fill check guarantees every key is reachable without its own lock, and that the exit sits behind the lock. 26 of the 32 Freedoom 2 maps are mixed in; 6 are held out for evaluation.

04Recurrent PPO at scale

  • From scratch (training/ppo.py): GAE (γ 0.995, λ 0.95), clipped PPO, BPTT through the GRU over 64-step segments with episode-boundary resets, return-scaled rewards, entropy annealing.
  • Asynchronous workers: each process runs 6 games with a shared-memory copy of the policy and returns whole trajectories. The GPU learner updates while the next rollout is collected (policy lag 1, corrected by the PPO ratio).
  • Double-buffered level boot: the next level is generated and booted in a background thread, so a finished episode never stalls the batch. This took us from ~1,000 to ~5,000 steps/s per 36-core box.
  • Modal fleet: several configurations train in parallel and warm-start from the best checkpoint; the best one, chosen on held-out maps, ships.

07Limits, stated plainly

  • Gauntlets and big real maps are the weak spot: dense ambushes still kill it half the time, and Freedoom's long levels with switch exits are rarely finished.
  • No pixels are used (rays + entities only). Exit pads and switches are not in the ray types, so exits are found by exploration rather than recognised.
  • Episodic memory recognises places, not routes: backtracking to a remembered locked door is learned, not planned.

08Engineering

  • The official validate.py passes; env/ is identical to the latest template; inference is self-contained in submission/.
  • 32 unit and integration tests: memory rotation-invariance, USE pulsing, step ≡ sequence equivalence of the GRU, generator solvability, official-env integration.
  • Weights 3 MB (Git LFS); one CPU thread; deterministic seeded sampling (temperature 0.75, chosen on held-out maps).
